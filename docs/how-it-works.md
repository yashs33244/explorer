# How the PostgreSQL field guide was made

This is the exact process behind `examples/postgres`, and what the skill automates.

## 1. Understand the code first

A code graph (graphify) mapped the repo into about 47,000 nodes and 843 communities. The 11 biggest areas became the first 11 topics (processes, parser, planner, executor, storage, MVCC, WAL, indexes, locks, catalogs, build and test). Later requests added Docker and the kernel, files on disk, memory, replicas, sharding, features, security and operations.

## 2. One researcher per topic, then a skeptic

Each researcher read the real source under `src/` and, where it could, ran real commands against a scratch server to see what actually appears on disk. It returned a strict JSON object (idea, analogy, steps with file and function, files to open, interview questions with answers and common traps, glossary, try-it commands).

A second agent then tried to prove it wrong. It found real mistakes in roughly a third of the topics, for example: the access-control rule is matched before the backend starts authenticating, some processes called "auxiliary" are not, a visibility rule was worded backwards, and a few functions lived in other files. Those corrections were applied before anything was drawn.

## 3. Diagrams are inline SVG, drawn by agents, judged by looking

For every topic an illustrator agent drew three SVGs by hand (as markup, not generated by a chart library): architecture, a numbered lifecycle, and the structure or anatomy. A small style kit keeps them consistent: dashed lavender blobs for groups, color-coded rounded boxes, line icons, labeled arrows, violet number badges. All colors are CSS classes, so the same file is right in light and dark themes.

The key step is the loop: each agent renders its SVG in headless Chrome inside the real page CSS, opens the PNG, and fixes what it sees (overlaps, clipped words, wrong arrow direction), in light and dark. Then a separate critic agent renders everything again with fresh eyes. About one topic in six needed a repair pass after that.

## 4. One builder assembles the page

`build-page.js` reads the topic JSON, the SVG files and one config file and writes a single HTML file: a sticky navigation rail, hero, overview diagrams, then a section per topic. Tables are sized by their content and scroll inside the page. Interview questions are collapsible and can be ticked off, with progress stored in the browser.

## 5. Publish

The HTML is published with the Artifact tool, which hosts it privately and keeps the same URL on every update.

## Why it works

- Facts come from real files and real runs, then get attacked by a second reader.
- Pictures are checked by looking at them, not by trusting the markup.
- Everything is data (JSON and SVG), so a topic can be fixed and the page rebuilt in a second.
